# 窗口置顶助手（TopMostPin）

把**任意窗口**钉在最上层 —— 一个便携的 Windows 桌面小工具。双击即用，无需安装。

- **两种置顶方式**：鼠标指向目标窗口按 `Ctrl+Alt+P`，或在界面列表里点窗口左边的图钉
- **便携**：单目录，数据全在 `data\`，删掉文件夹即彻底卸载
- **单色 light 界面**：黑白两色，无彩色。设计说明见 [`docs/design.md`](docs/design.md)

---

## 技术栈

**Tauri v2 + Rust + Vue 3 + Vite**，单 exe 便携版，零安装、零运行时依赖（除系统自带的 WebView2）。

选型基于本机实测，不是偏好：

| 事实 | 影响 |
|---|---|
| `cargo` 在本机**无法联网**（schannel 凭证问题） | 只能用离线缓存中的 crate。`tauri-plugin-global-shortcut`、`global-hotkey`、`image`、`async-broadcast` 都不在缓存中 → 全部不用 |
| Go 路线需要 Wails v2 作 WebView 宿主 | 缓存里只有 wails v1.16.9；且 gcc 缺失时 cgo 路线不可行 → 排除 |
| Windows 11 自带 WebView2 运行时 | Tauri 的运行前提已满足 |
| `windows-sys 0.61.2`、`winreg 0.55`、Tauri v2 全家桶 | 均已在离线缓存 → 直接调用 Win32，无需任何绑定生成器 |
| JDK 为 1.8（无 jpackage）、.NET 只有运行时无 SDK | 两者均无法构建可交付产物 → 排除 |

**核心结论：全局热键与窗口置顶全部走 `windows-sys` 直调，不依赖任何 Tauri 插件。**

## 用法

| 操作 | 结果 |
|---|---|
| 鼠标指向窗口，按热键（默认 `Ctrl+Alt+P`） | 置顶；再按一次取消 |
| 界面列表点左侧图钉 | 同上 |
| 界面点「全部取消」 | 一次取消所有置顶 |
| 设置页 → 热键 → 「修改」 | 按下新组合键即可换绑 |
| 关闭主窗口 | 收进托盘（程序继续守护已置顶窗口） |
| 双击托盘图标 | 重新打开界面 |
| 托盘右键 → 退出 | 真正退出，并自动取消全部置顶 |

## 热键

热键可以改。设置页点「修改」，然后直接按下想要的组合键。

### 两条约束，都在解析层拦住

| 约束 | 为什么 |
|---|---|
| **必须带至少一个修饰键** | 不带修饰键的组合一旦注册成功，那个键就被从**整个系统**里吞掉了 —— 单绑一个 `P`，任何程序都收不到 `P`。这不能指望 `RegisterHotKey` 报错，它不会 |
| 主键只支持字母 / 数字 / F1–F24 | 其余键位（方向键、多媒体键……）的虚拟键码在不同键盘布局下不稳定，宁可明确说不支持，也不静默降级 |

不认识的写法**直接报错**，不猜。静默降级最坏的地方是用户以为设置生效了，然后按下去没反应。

### 失败时不会把热键弄丢

换到一个已被其它程序占用的组合（本机 `Ctrl+Alt+P` 就是），流程是：

1. 先摘下当前热键 → 试着注册新的
2. 装不上 → **把原来的原样装回去**，再把错误码 `1409` 翻译成人话给用户看

摘掉旧的再装新的，中间那个空档是有意的：同一个 ID 不能同时注册两个组合。
而「装不上就恢复」这一步绝不能省 —— 否则用户试一次失败，热键就整个没了，
他会以为设置坏了，而不是「这个组合被占用，换一个」。

### 一个必须解释的现象

**已经被注册的组合，本程序收不到它的按键。** 系统会在窗口收到 `keydown` 之前
就把它截走（这正是全局热键的工作原理）。所以录制时按下一个被占用的组合，
界面上不会有任何反应。

这不能靠代码解决，只能靠说清楚：录制态超过 2.5 秒没收到按键，界面会主动提示
「如果这个组合已被其它程序注册，系统会先把它截走」，而不是让用户对着一个
没反应的框发呆。

### 记住它

生效的组合落库（`settings.hotkey`），下次启动**优先尝试它**，再退到候选列表。
否则机器上装的软件一多，可用组合一变，热键就会莫名其妙换掉，肌肉记忆直接失效。

### `--set-hotkey=` 脚本化配置

```
窗口置顶助手.exe --set-hotkey=Ctrl+Alt+Shift+F23
```

启动时套用指定热键并落库，给「装完直接配好」的脚本化部署用。
它走的是和界面「修改」按钮**完全相同**的链路，所以也是这条链路唯一能被自动
验证的入口（见 `scripts/hotkey-test.ps1`）。

## 启动动画

启动时先弹一个无边框小窗：图钉从上方落下、钉穿那条**水面线**（主界面里分隔
「已置顶」与其余窗口的同一条线），随后浮现应用名与一条进度线。约 1.1 秒。

### 它是原生 GDI 窗口，不是 WebView

第一版用 Vue 画在一个 WebView 窗口里，结果是**先白屏、再出动画**。原因很实在：

> WebView2 初始化要 1～1.5 秒，而窗口一显示就是白的。
> 启动画面存在的意义**恰恰是填住这段时间** —— 用 WebView 去画它，
> 等于把要填的洞变成了白屏本身。

改成原生 Win32 + GDI 之后，实测：

| | WebView 版 | 原生 GDI 版 |
|---|---|---|
| 窗口出现 | 进程启动后 ~1464 ms | **~33 ms**（创建耗时 6 ms） |
| 第一帧 | 一片白 | **就是动画的第一帧** |
| 白屏 | 有 | 无 |

几个必要的处理：

- **在 `tauri::Builder` 之前创建**，这正是它必须原生、且必须尽早的原因。
- **跑在独立线程的消息循环上**，与 tao 的循环完全隔离，互不干扰。
- **显示后立刻 `UpdateWindow`** 同步画第一帧 —— 少了这一步，窗口会先以
  「未绘制」的状态暴露一瞬，那一瞬就是白底。
- **GDI 没有抗锯齿**，所以图钉先按 4 倍分辨率画进临时位图，再用 `HALFTONE`
  缩放贴回。线条与文字不用管：前者轴对齐，后者由 GDI 自己抗锯齿。
- **先画图钉、再画水面线**：两者同为墨色，重叠处看不出接缝，而轴对齐的线不会糊 ——
  正好把「钉穿」的效果交给它。
- **本线程要显式声明 `SetThreadDpiAwarenessContext(PerMonitorV2)`**：
  进程级的 DPI 感知是 tao 之后才建立的，不声明的话本机 150% 缩放下
  `GetDpiForSystem()` 会返回 96，动画窗只有应为尺寸的 2/3（见踩坑记录第 13 条）。
- 单色的「淡入」做成**纸色→墨色的灰度渐变** —— 在黑白体系里这是合法的值过渡，
  不需要透明度。

### 何时收尾

**由前端决定**：`App.vue` 在首次绘制之后（两级 `requestAnimationFrame`）调用
`main_ready`，后端才关掉动画、显示主窗口。后端无从知道 WebView 什么时候
真正画出了内容，定时显示会让用户看到一个还没画好的界面。

兜底有两层：动画自己最多等 6 秒，后端另有看门狗在 6.8 秒强制放出主窗口 ——
万一前端脚本出错，用户也不会卡在「动画播完了但什么都没有」。

**热键是一组候选，不是一个固定值。** 依次尝试 `Ctrl+Alt+P` → `Ctrl+Shift+P` →
`Ctrl+Alt+T` → `Ctrl+Alt+A` → `Ctrl+Alt+W` → `Ctrl+Alt+K`，用第一个能注册成功的，
并把**实际生效的那个**显示在界面报头和设置页。全部被占用时，键帽会变成虚线，
提示也改说「点图钉置顶」。

这样做的原因很实际：本机 `Ctrl+Alt+P` 已被其它程序注册
（`RegisterHotKey` 返回 1409 `ERROR_HOTKEY_ALREADY_REGISTERED`），
写死单一组合在装了同类工具的机器上会直接失效。

## 管理员权限

**程序固定以管理员身份运行，这不是一个可选项，设置里也没有开关。**

> **非提权进程无法置顶提权进程的窗口。** 这是 Windows 的完整性级别限制（UIPI），
> 任务管理器、部分安装程序都属于这一类。`SetWindowPos` 会返回
> `ERROR_ACCESS_DENIED(5)`。

### 为什么不做成选项

因为它会被默认到错误的那一侧 —— 默认普通权限，等于**让工具在最需要它的场景下用不了**：

| 想置顶的窗口 | 实际运行身份 |
|---|---|
| Chrome / Edge | 管理员（本机实测） |
| idea64.exe / explorer.exe / QQ.exe | 管理员（本机实测） |

这些进程以管理员身份运行时，非提权进程调用 `SetWindowPos` 只会拿到
`ERROR_ACCESS_DENIED(5)` —— 这正是用户反映「普通权限根本置顶不了」的原因。

中间还经历过一版「默认开启的开关」。它比固定行为更糟：数据库里一旦存着
`run_as_admin=0`，就会看到一个**关不掉的普通权限状态**，而且这个不一致从现象上
根本看不出来。既然正确的取值只有一个，那它就不该是设置项。

### 提权怎么落实

进程令牌在启动后就固定了，**无法在运行中提权**，所以只能靠重启进程：

```rust
ShellExecuteW(null, "runas", exe, ...)   // 系统弹 UAC，同意后以高完整性令牌启动
```

- **提权失败不阻断启动**：UAC 被拒、或账户本身没有管理员权限时，继续以当前权限运行，
  设置页会说明「为什么有些窗口置顶不了」。
- **`--no-elevate` 可显式跳过**本次提权，给脚本调用和「我就想用当前权限跑一次」的场景。
- **有 60 秒防抖**（`last_switch_at`），避免重启失败后反复弹 UAC。
- 重启的握手靠 `data\.relaunching` 标记文件，而不是命令行参数 —— 环境变量跨提权边界
  不保证保留。

> 降权重启的能力已经删掉了。曾经为了那个开关存在过（让 `explorer.exe` 去启动，
> 它运行在中完整性级别，子进程自然也是），开关一删它就成了永远走不到的死代码。
> 死代码最坏的地方不是浪费，而是**让人以为那个能力还在**。

**为什么为此换掉了 `tauri-plugin-single-instance`：** 该插件的互斥体在 `Builder` 阶段
创建，重启时旧实例还没退出，新实例一启动就被判定为「重复启动」、唤醒旧窗口后自己退出。
用户看到的现象是*程序一闪即没*。改为自实现（`src/single_instance.rs`）后，
重启中的实例会**等待旧实例释放互斥体**再继续；顺带还甩掉了插件依赖链上 Linux 专用的
`zbus` / `async-broadcast`（那两个不在离线缓存里）。

**单实例检查必须在提权之前。** 否则「已经以管理员运行时再双击一次图标」会先弹一次
UAC，等用户点完才发现旧实例还在、唤醒它然后退出 —— 白弹一次。而「双击图标把窗口叫
出来」恰恰是最高频的操作。

## 数据与持久化

数据落在便携目录下的 **`data\data.db`**（SQLite 单文件）：

| 表 | 内容 |
|---|---|
| `settings` | 键值设置：`hotkey`（**用户改过的**热键，下次启动优先复用）、`last_switch_at`（提权防抖） |
| `pin_events` | 置顶事件历史：句柄、标题、进程名、动作、时间 |

为什么是 SQLite 而不是 JSON：置顶事件天然是「追加 + 按时间倒查」的形态，用 JSON
需要每次全量读写，写一半崩溃还会损坏文件。SQLite 事务安全，且 `bundled` feature
会把 sqlite3 一起编译进来，不依赖系统库 —— 与「便携、零外部依赖」一致。

**热键因此变得稳定**：注册成功的组合会落库，下次启动优先尝试它。否则机器上装了别的
软件（或那个软件被卸载）时，可用组合一变，热键就会莫名其妙换掉，用户的肌肉记忆直接失效。

`data\topmost-pin.log` 是另一个东西 —— 诊断日志，不是数据。GUI 子系统程序没有控制台，
`println!` 与 panic 信息都无处可去，出问题时只能盲猜，所以关键事件都写进这个文件。

已置顶的窗口在列表里**整行反相**（实心墨底），并排在列表最上方；与其余窗口之间以一条
2px 粗墨线分隔 —— 这条线就是「水面线」，之上是被抬起的窗口。

## 架构

```
src-tauri/src/
├── winapi.rs      Win32 直调层：枚举 / 标题 / 类名 / 进程名 / 置顶读写
├── pin.rs         置顶集合管理（Win32 通过 Win32Ops trait 注入，可脱离真实窗口测试）
├── hotkey.rs      热键线程：RegisterHotKey + SetTimer + 自有 GetMessage 循环
├── autostart.rs   winreg 直写 HKCU\...\Run
├── tray.rs        动态托盘菜单（已置顶窗口即为可点击的取消入口）
├── commands.rs    Tauri 命令层
├── events.rs      pin://changed / pin://error 事件
├── state.rs       全局状态
└── lib.rs         装配

src/               Vue 3 前端（types / api / stores / views / components）
```

### 两条独立的消息泵

```
主线程   ── tao 的 Win32 事件循环（WebView2 窗口 + Tauri 命令）
热键线程 ── 自有 GetMessageW 循环
             ├─ WM_HOTKEY → 切换光标下窗口的置顶
             └─ WM_TIMER  → 每秒重断言 + 剔除已销毁窗口
```

**为什么热键必须自建线程**：`RegisterHotKey(hwnd=NULL, ...)` 投递的 `WM_HOTKEY` 是**线程消息**
（窗口句柄为空）。Tauri 主线程的 `DispatchMessage` 对没有窗口的消息无处分发，会静默丢弃它。

## 三个关键设计决策

### 1. 置顶状态依据「自维护集合」，不读 `WS_EX_TOPMOST`

提示框、输入法候选窗、桌宠等窗口**天然**就带 topmost 位。若按 EXStyle 判断「是否已置顶」，
光标指向这类窗口时第一次按键会变成「取消置顶」—— 用户看到的是什么都没发生。

实测旁证：本机 `dsh-pet 桌宠（桌面模式）` 启动即带 topmost 位。

### 2. 重断言定时器与热键解耦

每秒把被别的程序抢回去的 `WS_EX_TOPMOST` 重新置位。只在**用户可见状态真的变化**时
（窗口被销毁而剔除）才发事件 —— 否则前端会被每秒唤醒一次。

### 3. 退出时自动取消全部置顶

程序退出后没人再维护置顶，留着只会让那些窗口永远赖在最上层。异常崩溃留下的残留，
重新运行并点一次「全部取消」即可清除。

### 关于端到端验收：一个环境限制

`acceptance-test.ps1` 在本项目的开发环境（DSH 自动化沙箱）里**无法完成置顶断言**，退出码 2。
这不是产品缺陷，已经用 A/B 对照证明：

| 调用方 | 进程深度 | 对系统外窗口（explorer / chrome / idea64）调用 `SetWindowPos` |
|---|---|---|
| DSH 直接派生的 pwsh | 直接子进程 | **成功**（`返回=True err=0`） |
| `cargo test` 派生的测试进程 | 孙进程 | **失败** `ERROR_ACCESS_DENIED(5)` |
| 被测应用（`Start-Process` 启动） | 孙进程 | **失败** `ERROR_ACCESS_DENIED(5)` |

同一 API、同一窗口、同一标志位，**只有进程深度不同**。一份用法显然正确的纯 Rust 控制台程序
（`probe_pinning_a_window_outside_the_sandbox`）与被测应用表现完全一致 —— 因此这是沙箱按进程深度
施加的限制，而不是代码问题。

`acceptance-test.ps1` 已经把这个对照做成**内置的控制条件**：它先跑 Rust 探针，探针也被拒时
就判定为环境限制并跳过（退出码 2），避免把环境问题误报成产品缺陷。

**最终确认方式**：把 `dist-portable\窗口置顶助手\` 整个目录拷到任意位置，**在资源管理器里双击 exe**
（这样它就是资源管理器的子进程，不受自动化沙箱约束），然后指向任意窗口按热键。

## 踩过的坑

1. **`[dependencies.windows-sys]` 子表会吞掉后续依赖**
   TOML 的表头一直生效到下一个表头。写成子表后，`serde`、`dirs` 等全部被归入该子表，
   静默失效 → 编译报「cannot find module `dirs`」。**必须写成内联表。**

2. **`RegisterHotKey` / `MOD_*` 不在 `WindowsAndMessaging`**
   它们在 `Win32::UI::Input::KeyboardAndMouse`，需要额外开 `Win32_UI_Input_KeyboardAndMouse`
   feature。

3. **`cargo metadata --offline` 会失败，但 `cargo build --offline` 正常**
   `tauri-plugin-single-instance` 依赖 Linux 专用的 `zbus` → `async-broadcast`，
   而后者不在缓存中。metadata 会解析**所有平台**，build 只取当前 target 所需。

4. **`tauri-plugin-autostart` 离线不可用**
   依赖链含未缓存的 `async-broadcast`。改用 `winreg` 直写注册表。

5. **`HWND` 在 windows-sys 里是裸指针且非 `Send`**
   不能直接放进跨线程集合。对外统一用 `isize`（`HwndRaw`），只在调用瞬间转回 `HWND`。

6. **release profile 不能用 `codegen-units = 1` + `lto = "fat"`**
   本机带实时防病毒扫描，rustc 写入后立即删除 40MB+ 目标文件时会被占用，报 `os error 32`。
   已改用 `lto = "thin"` + `codegen-units = 16`。

7. **bundled 的 `sqlite3.c` 在 dev / test profile 编不过**
   ```
   cl : Command line error D8050 : cannot execute 'c1.dll':
        failed to get command line into debug records
   ```
   dev / test profile 默认 `debug = true`，cc-rs 会据此给 C 编译器加 `-Z7`，而
   sqlite3.c 有 8MB 之巨，MSVC 塞不下。**这个坑特别隐蔽：`cargo build --release`
   一路正常，`cargo test` 却编不过。** 解法是给这个包单独关掉调试信息
   （见 `Cargo.toml` 的 `[profile.dev.package.libsqlite3-sys]`）。

8. **WebView2 在一个进程里只能用一个用户数据目录**
   启动动画是第二个 WebView 窗口，漏了 `.data_directory()` 就会直接创建失败，
   报错是「拒绝访问 (os error 5)」—— **完全看不出和缓存目录有关**。
   两个窗口必须传同一个目录。

9. **`Add-Type` 编译 C# 时默认不引用 `System.Drawing.Common`**
   在 C# 里写 `System.Drawing.Bitmap` 会 `CS1069`。位图那部分得放回 PowerShell 做
   （那里 `Add-Type -AssemblyName System.Drawing` 已加载该程序集）。

10. **debug 产物会带控制台窗口**
    `#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]` —— 控制台只在
    release 里被抑制（debug 要留着看 panic 与日志）。发布前务必确认交付的是 release
    产物，否则用户会看到一个黑窗。冒烟测试有两项专门盯这件事：
    PE 子系统必须是 `2 (Windows GUI)`，且进程不得创建 `ConsoleWindowClass` 窗口。

11. **冒烟测试必须用 `--no-elevate` 启动，否则会被「自我提权重启」骗到**
    程序固定以管理员运行，普通权限启动时它会自我提权重启（`ShellExecute runas`
    → 本进程退出 → 新实例接管）。而测试脚本跟踪的是最初那个 pid，于是得到一串
    看起来像产品故障的**假失败**：

    | 现象 | 真实原因 |
    |---|---|
    | 「进程存活」失败 | 第一个进程按设计退出了，把位置让给提权实例 |
    | 「第二次启动不产生第二个进程」变成 1→2 | 提权实例正在替换旧进程 |
    | 主窗口矩形 `0x0` | 抓到的句柄属于已销毁的启动动画窗/旧实例 |

    这个假象排查了很久，因为**它看起来完全是产品缺陷**。现在冒烟测试带上
    `--no-elevate` 启动（权限路径由下面的诊断脚本单独验证），并在启动前清掉
    `data.db*` 保证干净状态。`scripts/diag-single-instance.ps1` 是当时用来
    在干净环境里单独确认单实例/提权行为的诊断脚本，保留下来备用。

12. **启动画面不能用 WebView 画**（用户直接指出的问题：先白屏、再出动画）
    WebView2 初始化要 1～1.5 秒，窗口一显示就是白的。启动画面存在的意义恰恰是填住
    这段时间，用 WebView 画它等于把要填的洞变成白屏本身。改成原生 GDI 窗口后，
    窗口在进程启动后 ~33ms 就出现，第一帧就是动画本身。

13. **原生动画窗的 DPI 要自己声明**
    进程级 DPI 感知是 tao 在 Tauri 初始化时才建立的，而动画必须跑在那之前 ——
    不调用 `SetThreadDpiAwarenessContext(PerMonitorV2)` 的话，本机 150% 缩放下
    `GetDpiForSystem()` 返回 96，动画窗只有应为尺寸的 2/3（实测日志 `320x196 @1.00x`，
    正确值是 `480x294 @1.50x`）。线程级设定只影响这个窗口，不干扰 tao 之后对进程的设定。

14. **按标题找窗口必须限定进程**
    标题里含「窗口置顶助手」的窗口不止主窗口一个：资源管理器开在这个目录下时，
    文件夹窗口的标题就长这样，而且比主窗口还大。冒烟测试的
    `FindLargestByTitle` 因此把主窗口量成了 `2558x1526`（实际是 `1432x1076`），
    也解释了一次莫名其妙的 `0x0` 假失败。加上 pid 限定即可。

## 已知限制

- **提权失败时无法置顶提权的窗口**。程序固定尝试以管理员运行，但 UAC 被拒、或账户
  本身没有管理员权限时只能以普通权限继续 —— 此时对提权窗口调用 `SetWindowPos`
  会拿到 `ERROR_ACCESS_DENIED(5)`（Windows 的完整性级别限制 UIPI）。
  界面会明确说明原因，不会静默失败。若用 `--no-elevate` 启动，等同此情形。
- **热键可能与其它软件冲突**。候选列表会依次退让，界面上显示的是**实际生效**的那个；
  仍然冲突就在设置页换一个（见上面的「热键」一节）。
- **不显示窗口图标**。图标需要 PNG 编码，而 `image` crate 不在离线缓存中。
  列表改用等宽字体的进程名 + 类名 —— 这本来也更可扫读。
- **不持久化置顶状态**。窗口句柄重启后即失效，存了也没有意义。
